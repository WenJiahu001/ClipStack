# 性能优化报告

更新日期：2026-10-28，程序 v0.2.0。环境：Windows 10 22H2 x64，.NET 10.0.13，Release 构建。

## v0.2.0 查询与图片链路

- 主列表首次查询只读取 100 条和一条探测记录，滚动时追加；搜索仍匹配完整正文，找到当前批次所需数量后停止遍历。
- 查询使用独立只读连接和查询锁，WAL 下长文本解密不占用写锁；内容修订号保护缓存失效，防止删除或备注修改后的旧查询重新填入缓存。
- 图片采集编码、历史图片回写和原图预览共用一个后台重任务槽，避免这些路径同时完整解码多张大图。剪贴板快照、系统复制及缩略图仍有独立开销，任务槽不是进程内存上限。
- 搜索或分类变更立即禁用旧结果操作，成功应用最新查询后恢复；分页保留已有对象和选择。

1,000 条、每条约 6,000 字符及 100 条带备注收藏的本次基准中，首次读取首批 100 条及一条探测记录约 **104.61 ms**，随后完整读取 1,000 条约 **838.41 ms**。重复完整读取中位数 16.26 ms，全文末尾搜索中位数 59.36 ms。首次读取为单次样本，包含相关 JIT 与解密；未清空文件缓存，不能视为完整 UI 冷启动，也不能与下文历史基准视为同次运行。原始数据为 `performance-v0.2.0.json`。

60.02 秒持续检查完成 **1,906 轮**合成文本与图片的并发查询、保存、取消和定期清理，回读核对通过；进程峰值工作集 **107.3 MiB**。这只是指定合成负载和短时测量，不代表大图场景的最坏峰值，也不等于 24 小时常驻。原始数据为 `持续运行检查.json`。

## 10,000 条长文本边界

另建独立合成目录，10,000 条文本、每条约 6,000 字符、1,000 条收藏备注，超出全文缓存容量；常规操作取 3 次中位数，首次读取仅取单次样本。

| 操作 | 当前机器耗时 |
| --- | ---: |
| 首次读取首批 100 条及一条探测记录 | 93.88 ms |
| 首批后完整读取 10,000 条 | 8,595.55 ms |
| 重复读取 10,000 条（摘要命中） | 150.57 ms |
| 全文末尾搜索（遍历全部记录） | 8,555.39 ms |
| 无匹配全文搜索 | 8,357.92 ms |
| 收藏筛选 | 50.93 ms |
| 满额新增并淘汰 | 48.38 ms |

大规模完整正文搜索仍有明确开销：本场景一次扫描累计托管分配约 296 MiB，并非同时存活内存；全文缓存较小，扫描仍需解密大量正文。独立读取连接和后台任务减少对写入与界面线程的占用，取消逐行检查，但没有把无匹配搜索变成毫秒级查询。首批加载约 94 ms 也只是查询耗时，不含窗口初始化及渲染。

原始数据为 `performance-10000-v0.2.0.json`。为保留当前加密落盘和有界内存，本次未引入明文全文索引或扩大到覆盖所有正文的缓存；后续若要进一步降低这一场景的搜索延迟，需要单独评估搜索索引的存储和隐私取舍。

## 检查范围与已实施优化

| 链路 | 发现的问题 | 已实施的优化 |
| --- | --- | --- |
| 历史查询 | 每次呼出、搜索、刷新都重新 DPAPI 解密正文与备注 | 进程内摘要/备注缓存与全文缓存，各有 16 MiB 估算容量上限；变更按记录失效 |
| 筛选 | 先读取所有行，再在 C# 中排除类型或非收藏记录 | 筛选下推 SQL，减少托管对象和解密工作 |
| 长文本列表 | 每条记录保留 4,096 字符摘要，实际只显示三行 | 摘要降至最多 512 字符，避免截断 UTF-16 代理对；搜索和复制仍使用完整内容 |
| 快速搜索 | 旧查询继续占用单个数据库连接，结果只在返回后被丢弃 | 新搜索取消旧请求，查询逐行检查令牌；递增序号继续防止旧结果覆盖新结果 |
| 刷新 | 每次重新创建所有列表项并替换 ItemsSource | 按 ID 复用记录对象；无增删和顺序变化时保留列表与选择 |
| 连续采集 | 保存回调等待完整列表刷新和缩略图解码，阻塞下一条保存 | 保存与刷新分离；约 120 ms 合并刷新，持续采集也定期刷新，不反复中断首次查询 |
| 原图预览 | 单纯选中记录就读取全文或解码大原图 | 选中时仅更新摘要；主动查看时加载全文/原图，关闭预览后释放视图引用 |
| 缩略图 | 每次刷新重新解码前 24 张，后面的图片不加载 | 随可视区域附近的卡片按需加载；最多两个并发任务；离屏撤销请求并清除卡片图片引用 |
| 图片缓存 | 缺少复用与明确内存预算 | 最近使用缓存限制估算 8 MiB / 128 项；计入编码字节及解码像素。大原图回退按最长边约 320 像素解码 |
| PNG 采集 | 完整 PNG 解码仍在 UI 线程 | 关闭剪贴板锁后，将 PNG 解码与原有统一编码放到后台；保留格式间的去重规则 |
| 存储淘汰 | 未超额也构建所有普通历史候选列表；超一条也读取全部候选 | 合并统计查询，未超额提前返回；只受条数限制时按实际缺额查询候选，图片压力时排除不需要淘汰的文本 |
| 启动 | 前台启动查询两次，后台启动也加载历史列表 | 前台先显示面板，只发出一次刷新；后台启动不预载列表，首次呼出时加载 |

保留现有事件驱动监听、队列上限、WAL 和 FULL 同步、DPAPI 加密、写连接同步及事务回滚机制。空闲时没有新增高频轮询；未新增第三方依赖。

## 历史前后基准（2026-10-22）

使用相同的确定性合成数据：1,000 条文本，每条约 6,000 字符，100 条收藏并带备注。优化前后各使用独立数据目录。除首次查询取单次结果外，其余取连续 7 次操作的中位数。首次读取指新 `HistoryStore` 的第一次查询，包含相关 JIT 和解密；未清除操作系统文件缓存，不能视为整机冷启动。

| 操作 | 优化前 | 优化后 | 说明 |
| --- | ---: | ---: | --- |
| 首次读取 1,000 条 | 874.40 ms | 891.11 ms | 基本持平，首次仍需解密，没有宣称冷启动加速 |
| 重复读取 1,000 条 | 860.62 ms | 16.96 ms | 缓存命中后减少约 98% |
| 搜索完整正文末尾 | 870.81 ms | 58.00 ms | 匹配摘要外的正文，减少约 93% |
| 全文无匹配搜索 | 856.78 ms | 45.37 ms | 减少约 95%，仍需遍历文本 |
| 收藏筛选 | 114.16 ms | 5.07 ms | SQL 筛选与缓存复用 |
| 空图片筛选 | 10.68 ms | 5.42 ms | SQL 筛选；绝对耗时较小 |
| 满额新增并淘汰 | 21.33 ms | 8.77 ms | 只读取所需候选，仍执行持久事务 |

重复查询每次托管分配从约 37.54 MiB 降至 0.23 MiB；全文末尾搜索从约 29.56 MiB 降至 0.22 MiB。数据来自 `GC.GetTotalAllocatedBytes`，不包含 WPF 原生内存。以上是当前机器、合成数据和缓存已命中条件下的测量，不是所有机器的性能承诺，也不等于完整 UI 呼出时间。

原始数据：发布目录 `performance-before.json`、`performance-after.json`。

## 内存取舍与边界

- 通过有限的已解密文本缓存换取更少的 DPAPI 调用。基准结束时的工作集快照约从 49.8 MiB 增加到 62.8 MiB；快照还受 GC、JIT 和系统页面驻留影响，不能作为稳定或峰值内存结论。
- 摘要缓存、全文缓存和缩略图缓存合计估算上限 40 MiB，按需增长，并非启动时预分配。条目与运行时对象有额外开销，缓存预算不等于整个进程的内存上限。
- 主列表的摘要从每条最多约 8 KiB 的字符数据降至约 1 KiB；10,000 条最大设置下的摘要字符数据约从 78 MiB 降至 10 MiB，尚未计入对象、备注和 UI 开销。
- 缓存不写入数据库、日志或明文搜索索引。删除、清理、备注修改和退出释放相应引用；托管字符串的实际回收由 GC 决定，不承诺立即擦除内存。
- 超出全文缓存容量的大量长文本搜索仍会重新解密和扫描，首次解密也仍有成本；取消过时请求可避免无用扫描，独立读取连接减少其对保存的影响。
- 查看大原图、图像处理及剪贴板快照会临时使用较多内存；这些不计入缩略图缓存预算。完整图像处理共享任务槽，DIB 来源的快照读取仍受来源程序及 STA 剪贴板调用限制。
- 保留自包含单 EXE；未启用有兼容风险的 WPF 裁剪，也未降低数据库持久性设置来换取测试分数。
